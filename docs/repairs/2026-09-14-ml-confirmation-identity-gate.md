# 美客多月结确认人身份门禁

## 问题与影响

2026-08 V4 运营确认卡由潘志聪误点后，服务仍把月结推进为“运营已确认”，并生成了财务确认卡。报表生成与金额未出错，但确认来源不符合业务规则：运营确认必须由梁俊辉完成，财务确认必须由林纯子完成。

错误财务卡已先原卡撤销并移除按钮。撤销时所有公司汇总、工资、提成、最终核销和付款放行标记仍为 false。

## 根因

`app/ml_close.py::_confirm_action_impl` 只把回调人员字段用于展示和留痕，没有在状态读取、动作占用、报表生成或下一张卡发送前校验指定负责人。展示姓名也不能作为权限依据，因为姓名可缺失、重复或来自不同飞书 App 的身份空间。

首次撤销错误财务卡后，既有成本审计定时流程又在错误状态仍为“运营已确认”时生成了第二张财务卡。事故恢复入口当时只固定第一张卡 ID，因此虽能安全拒绝写入，却无法证明所有错误入口都已失效。根因是一次性恢复证据模型只覆盖“一个错误卡片”，没有覆盖同一错误状态派生出的全部卡片。

## 修复

- 在当前历史卡片 App3 的同一身份空间内分别配置运营和财务确认人。
- 仅限制四个可放行动作：运营确认、运营豁免、财务经营暂结确认、财务最终确认。
- 只信任回调里的 `operator_id/open_id`；`operator_name` 仅供界面展示，不能绕过校验。
- 身份不符、身份缺失或负责人配置为空时，在读取月结状态、占用动作记录、生成报表或发下一张卡之前直接停止。
- 未授权点击不 PATCH 共享原卡，避免其他群成员误点后让真正负责人失去入口。
- 运营/财务退回及成本重算动作保持原行为，本次 P0 不扩大权限范围。
- 增加本次事故专用、不可泛化复用的锁内恢复入口。它固定核对 2026-08 状态记录、错误操作人、已撤销财务卡、V4 哈希和完成标记、公司汇总仍为 V3，任一条件变化即停止。
- 恢复写入载荷仅含“状态、运营确认人、运营确认时间”三项；写后重新核对其余状态字段、实时数据哈希、V4 标记和公司汇总链接。事故状态一旦恢复，入口因前置状态不再匹配而自动失效。
- V3 的“经营暂结确认人、经营暂结确认时间、经营暂结报表链接”属于已完成历史凭证，不是本次 V4 误确认。恢复前必须与固定 V3 证据精确一致，恢复写入不得包含这三项，恢复后再次逐项核对保持原值；任一项漂移都在读卡或写表前停止。
- 恢复入口固定登记两张已知错误财务卡，且状态台最后卡片必须精确等于第二张。恢复前逐张用原发卡 App3 读取并结构化检查：必须已更新、未删除、显示撤销结果且不含按钮/回调；缺少任一张、任一张仍可点击或出现未知最新卡都会在写表前停止。
- 预演指纹改为同时绑定两张卡的 ID 与完整卡片文档；响应回传已核验卡片集合。本地 runner 还分别记录两张卡的内容 SHA256，正式恢复前后必须一致。
- 增加唯一部署标记 `ml_identity_recovery_card_set_v1_20260915`；runner 同时要求旧恢复标记、V3 保留标记和双卡标记，防止旧容器误通过上线检查。
- 恢复入口默认只预演；正式写入必须提交同一次预演生成的指纹。预演指纹绑定状态台完整前镜像、已撤销卡结构、V4 标记、公司汇总月份和旧链接，任一项变化都会拒绝写入。
- 飞书写入响应丢失时先固定记录回读：只有精确读到目标状态且其他字段未变才算成功；仍为原状态或出现第三种状态时均停止并禁止自动重试。恢复后按现行月结公式真实计算四项下游放行标记，必须全部为 false。
- 事故前置状态进一步锁定误确认时间 `1789376638046`；确认人或确认时间任一变化，都会在读取错误卡片和写入状态表前停止。保留既有可选状态表配置规则：配置为空时使用已核验固定记录，配置成其他表时拒绝恢复。
- 增加唯一部署标记 `ml_identity_recovery_exact_time_v1_20260915`，用于证明线上容器确实包含本次精确时间保护。
- 三字段恢复成功后的补发运营卡仍须遵守“不新增生产数据库、专用接口或环境变量”的边界；一次性本地 runner 待第 4 步完成收窄和独立复核后才可执行，当前旧脚本禁止运行。

## 生产恢复边界

先用原发卡 App3 只撤销第二张错误财务卡并逐张回读两张卡均无按钮；撤卡前后 Base 固定记录必须完全一致。部署并回读双卡健康标记后，才允许把 2026-08 月结从错误的“运营已确认”恢复为“待运营确认”。只清除错误运营确认人和时间，保留 V4 报表、哈希、47 列财务复核表及所有历史证据。随后只向梁俊辉 App3 身份生成一张新的运营确认卡，必须由梁俊辉本人点击；财务卡须在该点击后由系统重新生成，并由林纯子本人点击。

生产调用统一走默认只读的本地恢复脚本 `D:\Documents\财务与资产\.codex\plan\2026-09-07-mercadolibre-september-diagnosis\p0_restore_wrong_ops_confirmation.py`。脚本先保存预演证据；`--commit` 时先把完整状态前镜像、V4 与公司汇总证据写入唯一临时文件，强制落盘后再原子发布为交易文件，已有交易文件绝不覆盖；随后才把预演指纹交给锁内恢复入口。前后状态均由 App1 直接 GET 固定记录，不调用可能自愈表结构的通用状态接口。调用方必须解析 JSON 的 `status` 和写入结果，不以 HTTP 200 作为成功依据。

恢复完成后先停在“待运营确认”，再进入独立的第 4 步补发卡。现有 `p0_send_recovered_ops_card.py` 仍依赖已撤回的专用接口，当前禁止运行；必须先把它收窄成固定 `uuid` 的本地一次性 App3 发送器并完成复核，才允许向梁俊辉发送。

未纳入本次 P0 的风险：退回/重算动作尚未按角色限制。它们不能错误放行资金结果，但群成员误点可能触发退回，登记为后续 P1 权限加固。
